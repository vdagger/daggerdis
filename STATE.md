## Что это за проект

P2P голосовая рация и клиент для созвонов: чистый Rust, транспорт iroh/QUIC
(датаграммы для голоса, отдельное соединение для видео), GUI на eframe/egui.
Без серверов: комнату держит один из участников, при его выходе — миграция хоста.
Уже работает: голос (2 входа, эффекты, PTT), звонки, друзья, онлайн-статус, DM-чат,
трансляция экрана 1080p/1440p 30/60 fps звездой publisher → host → viewers.

- Объём: ~15 400 строк в `src/` (46 файлов), крупнейшие — `gui/mod.rs` (2 317),
  `network/video_link.rs` (2 043), `calls.rs` (898).
- Тесты: 95 юнит-тестов (config, calls, txbus, mixer, message, video_link,
  video_directory, presence, room, audio) — все зелёные на 2026-11-21.
- Платформы: Windows — основной таргет (видео только Windows);
  Linux/macOS собираются частично, готовность — в `ROADMAP.md` → «Кроссплатформенность».

## Известные проблемы и долги

- **Hot-plug проверен не до конца:** сценарий «выбранное устройство выдернули →
  откат на устройство по умолчанию» покрыт юнит-тестами плана
  (`devices::plan_device_update`) и кодом отката, но живьём не воспроизведён:
  Windows после нескольких `disable/enable` ответила «Device is pending system
  reboot» и отключить выбранную карту не дала. Проверить руками: выдернуть
  USB-карту при работающем приложении — должен быть тост
  «Устройство отключено: …», звук уходит на устройство по умолчанию.
- **Выдёргивание драйвера чтением конфигурации не лечится:** если выдернуть карту
  насовсем, `config.ini` сохранит откат (устройство по умолчанию), и после
  возврата карты выбор сам не вернётся — надо выбрать руками.
- **Групповая комната принята 21.11.2026 (вечер):** три узла, «Выйти из эфира»
  → «Позвонить» → «Войти», роли хоста, все комбинации трансляции. Подробности —
  ниже, в точке остановки. Причина, по которой раньше «не прокликивалось», —
  координаты кликов с масштабированного превью, а не поведение приложения.
- **Формат вывода на виртуальных 7.1 (21.11.2026, по жалобе друга на Razer):**
  драйвер таких устройств отдаёт f32, но воспроизводит его перекошенно — i32
  на нём звучит чисто (подтверждено автором в RustAudio/cpal#892). Правило
  выбора формата вынесено в чистую `audio::plan_output_candidates`: имя
  устройства с «7.1»/«razer»/«surround»/«virtual» → i32, затем i16, затем f32
  (формат важнее числа каналов); обычное устройство → меньше каналов, f32 для
  стерео. Плюс ручной выбор `output_format=f32|i32|i16` в настройках звука и
  поддержка `u8` (часть Windows-машин отдаёт только его — раньше в этом случае
  поток не открывался вовсе). В журнале теперь пишется причина: «формат: I32
  (виртуальный 7.1: i32 надёжнее)».
- **Найденный по ходу баг (исправлен):** кандидаты форматов строились только на
  48 кГц, поэтому на устройстве с 44.1 кГц (наш QUAD-CAPTURE) список был пуст и
  работал лишь формат по умолчанию — ручной выбор i32 молча игнорировался.
  Теперь частота берётся устройством: 48 кГц, если умеет, иначе его собственная.
- **Защита голоса от потерь — адаптивная (21.11.2026):** 8 % — только
  стартовое значение. Раз в секунду `tune_voice` берёт потери и полосу из
  `link_stats()` и зовёт чистую `mixer::plan_voice_tuning` (сглаживание ±4 %,
  потолок 30 %, ступень вниз по битрейту, если полосы меньше 1.3 от нужной).
  Правило покрыто тестами; живьём на чистом канале счётчик FEC остаётся 0.
- **Счётчики приёма голоса живьём не спровоцированы:** на loopback-соединении
  потерь нет, поэтому в панели диагностики все нули — это правильные нули, но
  ветку «провал буфера / маскирование / перезапуск потока» надо увидеть на
  реальной сети или плохом Wi-Fi. Логика окна (дельта счётчиков) покрыта тестами.
- **В отчёте нет отдельной цифры джиттера:** потери голоса в процентах уже
  есть (`rx_line`), джиттер виден косвенно — провалы буфера и адаптивный
  предбуфер. Отдельная цифра (разброс задержки прихода) — когда понадобится.
- **Хоткей: решения отдельно от ОС (21.11.2026):** `HotkeyState::step` —
  чистая машина (края PTT от тумблера/клавиши/экранной зоны, Ctrl+M по фронту),
  поток Win32 только читает клавиши и зовёт её. Бэкенду X11/Wayland останется
  прочитать состояние и позвать `step`; самих бэкендов пока нет.
- **Тесты очереди зрителя (21.11.2026):** `RemoteQueue` (дедлайн буфера,
  ожидание IDR после сброса, переполнение на пределе 270 кадров) и `Recent`
  (`handoff` от последнего ключевого, пустой хвост без IDR). Всего тестов 160.
- **Правила приёма — в `network/admission.rs` (21.11.2026):** `admit_sync`,
  `admit_room_chat`, `admit_members` — чистые функции, покрытые тестами
  (подлинность, глубина релея, «свой хост», блокировка приглашения, «вне
  эфира», членство и номер комнаты). Обработчик iroh только печатает причину.
- **Кроссплатформенность (21.11.2026):** платформенные модули закрыты
  `#[cfg(windows)]` (`video::win_*`, `publisher`, `video_session`, `tray`),
  `keybind` вне Windows не запускает пустой поток, `firewall` пишет, что
  правило не нужно; macOS собирается в `.app` скриптом `tools/macos-bundle.sh`
  (Info.plist с разрешениями на микрофон и локальную сеть, ad-hoc подпись).
  **Не проверено сборкой:** Linux/macOS-тулчейнов в этой среде нет —
  проверялся только Windows-билд и синтаксис скрипта (`bash -n`).
- **`gui/mod.rs` разнесён (21.11.2026):** было ~3 200 строк в одном `impl
  RadioApp`, осталось ~880. Оверлеи и панели — в `gui/`, теперь и части
  `update`: `update_video` (публикация, маршрут, приём кадров) и `update_tray`
  (меню иконки, «крестик», опрос скрытого окна).
  Оверлеи и панели живут в `gui/`: `settings_overlay`, `chat_overlay`,
  `call_overlay`, `diagnostics_panel`, `video_panel`, `console`, `persist`,
  `devices_ui`. Дальше дробить `update` (401 строка) — по мере надобности.
- **Тестов нет на GUI, network/iroh_service, video-win** — только чистые модули.
- Старый конфиг `config.ini` совместим, но ключи `mic_processing` / `input*_profile`
  остаются «мёртвыми» для новых установок.
- Проверить на живой машине после пачки 21.11: мьют (кнопка и `Ctrl+M`),
  тост при ошибке переключения динамиков, «Войти в комнату» из строки друга,

   Выйти» — можно причесать (сейчас это живой индикатор комнаты).

**Находка про инструмент:** клики мыши «перестали работать» из-за залипшей
боковой кнопки (`mouse_event(0x0084)` вместо `0x0100` XUP) — лечится
`mouse_event(0x0100, 0, 0, 1, 0)`; DSH висит поверх Albus, поэтому окно надо
поднимать `SetWindowPos(HWND_TOPMOST)` + Alt-трюк, со свежим handle (eframe
пересоздаёт окно после resize). Подробности в `AGENTS.md`.

## Видео: буфер, качество и честные 60 fps (21.11.2026, поздний вечер)

Проверка «достаточный ли буфер, идеальное ли качество, честные ли 60 fps
зрителю» — сначала измерениями, потом правками. Это опорные числа для игры в
1080p60 на этой машине (RTX 5080, Ryzen 7 7800X3D, экран 1920×1080@74).

**Замеры пробником** (`tools/video_probe`, headless, без сети):

| Проверка | Результат |
|---|---|
| `--capture 5` | 376 кадров за 5.01 с = **75.0 fps** (частота экрана) |
| `--gpu 1920 1080 60 600` | 600 кадров за 2.97 с = **202 fps** (NV12 на GPU → энкодер) |
| `--loopback 1920 1080 60 600` | 600 → 599 кадров за 5.09 с = **117.6 fps** (энкодер + декодер) |

То есть захват и кодирование держат 60 fps с двукратным запасом, и узкое место
было не в них.

**Живой прогон (два узла, трансляция всего экрана 1080p60, окно в движении):**

| | до правок | после |
|---|---|---|
| показ у зрителя | **44–46 FPS** | **58–61 FPS** |
| обновлений GUI | 72–74/с | 71–75/с |
| в очереди зрителя | 24 кадра (0.4 с) | 24 кадра (0.4 с) |
| выброшено кадров | ~16/с (молча) | 0–8 на окно 5 с |
| буфер по умолчанию | 2000 мс | **400 мс** |
| старт показа | до 2 с буфера + хвост от IDR | ключевой сразу (по просьбе), очередь 0 |

**Что было сломано и почему это важнее цифр:**

1. **Буфер 2 с — это задержка, а не качество.** Зритель игры видел происходящее
   на два такта позже и слышал голос «сейчас». Дефолт снижен до 400 мс
   (24 кадра при 60 fps), ползунок 0…5000 остался: плохому каналу — больше.
2. **Унаследованное отставание.** Хвост для вошедшего зрителя отдавался от
   последнего ключевого кадра без ограничения возраста: IDR мог быть двухсекундной
   давности, и зритель навсегда отставал на буфер + этот хвост. Теперь хвост не
   старше 500 мс, а свежий IDR издатель выдаёт **по просьбе** при подписке
   (`CODECAPI_AVEncVideoForceKeyFrame`), плюс GOP сокращён с 2 с до 1 с.
3. **Показ терял кадры в самом GUI.** Во-первых, в `Renderer` был один слот под
   декодированный кадр: два кадра, созревших в одном апдейте, — второй терялся
   (ровно те 44 из 60). Теперь короткая очередь на 3 кадра. Во-вторых, стоял
   искусственный период показа `0.75 × (1/fps)`: при 74 Гц апдейты идут через
   13.5 мс, любой на 12.5 мс отбрасывался, кадр ждал ещё один. Период убран —
   потолок задаёт сам поток.
4. **Очередь зрителя могла накопить секунду лишних кадров на старте** (пока
   создаётся декодер) и носила их весь сеанс: приход и показ идут с одной
   частотой, очередь не рассасывается. Предел стал `буфер + 24 кадра`; всё, что
   выше, сбрасывает очередь и ждёт ключевой (на старте это даёт ~1 с ожидания
   вместо вечного отставания).
5. **Качество было фиксированным.** Пресет считался только по разрешению:
   1080p → «сбалансированный» 8.7 Мбит/с, без выбора. Теперь в карточке
   трансляции есть список пресетов («Авто» / «Экономный» / «Сбалансированный» /
   «Качество», до 14.9 Мбит/с на 1080p60), он сохраняется в `video_preset` и
   показывает ориентир по полосе. Энкодер дополнительно включает CABAC, просит
   0 B-кадров, «качество/скорость» = 50 и VBV (пик 1.25 среднего, буфер 0.5 с) —
   `ICodecAPI` не принял только `realtime` и `b-pictures`, это записано в журнал.
6. **Карточка врала о размере**: показывала размер превью (960×540) как размер
   потока. Теперь — реальные 1920×1080, фактический битрейт и «смотрит хост»,
   когда поток уходит хосту через релей (раньше в этом случае было «0 зрит.»).

**Как это видно в журнале** (новые строки раз в 5 с):

```
[ВИДЕО] NVIDIA GeForce RTX 5080 1920x1080 → 1920x1080 @ 60 FPS · пресет Сбалансированный · 8.7 Мбит/с · MFT NVIDIA H.264 Encoder MFT
[ВИДЕО] показ 60 FPS (обновлений 75/с) · захват 60 FPS · 8571 кбит/с · пресет Сбалансированный · ждали GPU 302 · выброшено 0
[ВИДЕО] приём: показ 59 FPS (обновлений 73/с) · в очереди 24 кадров · декод 2.3 / GPU 1.0 / картинка 1.5 мс · ждали GPU 298 · выброшено 0
```

Проверено на двух узлах в трёх раскладках: издатель-гость → релей хоста;
издатель-хост → прямая подписка (в журнале `Зритель подписался` и
`Нужен ключевой кадр — просим энкодер выдать IDR`); повторный старт после
«Стоп». Тесты: 178, clippy 34 (базовая линия).

**Чего ещё нет для «идеального 1080 для игр»:**

- эксклюзивный полный экран (не borderless) и смена разрешения/alt-tab: DXGI
  Desktop Duplication отдаёт `DXGI_ERROR_ACCESS_LOST`, а `publisher` на этом
  завершает поток вместо пересоздания дупликации — стрим умирает молча;
- HDR и 10-битный цвет не поддержаны (BGRA 8 бит на всём пути);
- экран с частотой 144 Гц транслируется в 60 fps: захват идёт по кадру раз в
  1/60 с, но кадры между ними не выбираются (не «самый свежий»);
- камеры как источника нет (нужен Media Foundation Source Reader), телефонов
  тем более — им нужен свой отправитель, это отдельный транспорт.
